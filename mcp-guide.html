Learn MCP Visually

The Model Context Protocol — an open standard that lets AI apps plug into any data source or tool. Think of it as “USB-C for AI applications.”

Open standard · Anthropic 2024 Transports · stdio, Streamable HTTP Primitives · Tools, Resources, Prompts Now · 10,000+ servers

01The problem MCP solves

Before MCP, every AI app had to write its own one-off integration for every data source. That meant N×M custom connectors, each with its own auth, schema, and API.

Before — point-to-point spaghetti

Every app ↔ every service needed a bespoke adapter. Fragile, duplicated, impossible to scale.

After — one protocol, many plugs

Each app implements MCP once. Each service exposes one MCP server. They connect like USB devices.

02Architecture: the three roles

An MCP conversation has exactly three participants. Understanding who talks to whom is 80% of the protocol.

MCP host ↔ client ↔ server. The client is a thin adapter inside the host, one per server connection.

◆ Host

The app you use. Owns the model, the context window, and decides when to call servers. Handles OAuth and permission prompts.

Claude Desktop · VS Code · Cursor · opencode

◆ Client

Runs inside the host, one per MCP server. Maintains the connection and speaks JSON-RPC. The host can run many clients simultaneously.

◆ Server

A standalone program exposing capabilities — tools, resources, prompts — over a transport. Multiple hosts can share one server.

04Lifecycle: the initialize handshake

Every session starts with a handshake. The client and server announce their capabilities and negotiate a protocol version — then discovery begins.

Messages are JSON-RPC 2.0

// a tool call
{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "Paris" }
  }
}

Three message shapes

  • Request — client → server, expects a response.
  • Response — the answer, keyed by the request id.
  • Notification — one-way fire-and-forget, no id, no reply.

Errors come back as JSON-RPC error objects with codes — including ProtocolError, InvalidRequest, MethodNotFound, and NotInitialized.

05Transports: how messages travel

The same protocol runs over different pipes. stdio for local tools, Streamable HTTP for remote services.

06A minimal server in Python

About 20 lines is all it takes. This server exposes one tool that the model can call through any MCP host.

# weather_server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Weather")

@mcp.tool()
def get_weather(city: str) -> str:
    """Return current weather for a city."""
    return f"{city}: 22°C, partly cloudy"

if __name__ == "__main__":
    mcp.run()  # stdio by default

Wire it up in a host

# Claude Desktop config
# claude_desktop_config.json
{
  "mcpServers": {
    "weather": {
      "command": "python",
      "args": ["weather_server.py"]
    }
  }
}

The host spawns the process, the handshake runs, and get_weather becomes callable by the model — no HTTP endpoint needed.

07Your mental model

Five sentences that capture everything above:

1 One protocol

JSON-RPC 2.0 with an initialize handshake that negotiates capabilities and version.

2 Three roles

Host owns the LLM, client adapts the connection, server exposes capabilities.

3 Three primitives

Tools (model does), Resources (app reads), Prompts (user picks).

4 Two transports

stdio for local, Streamable HTTP for remote — same messages on both.

5 Build once, reuse

One server works in every MCP host, and every host works with every server.
